# APM 4.7 C 项存储与日志修复回植设计

**日期：** 2026-07-22
**目标分支：** `rover-4.6.3-deleteTest`
**目标板：** `dimah743`，Rover，DDS enabled
**设计状态：** 用户已批准范围，等待书面设计复核后进入实施计划

## 1. 目标

在保留当前 4.6.3 裁剪架构、本地 Patrol/Exact Pivot 实现和板级默认参数的前提下，回植 Rover 4.7.0 中 C 项的存储可靠性与日志能力：

1. C1：更新 ChibiOS SD 驱动，修复卡异常时 watchdog、线程永久睡眠和 bouncebuffer 错误清理问题。
2. C2：在高内存 H7 上使用可回退的 32KB FATFS/Logger I/O，同时维持默认总 RAM 预算。
3. C3：Rover armed 状态下即使重新启用 safety，也保持日志继续写入，直至真正 disarm。
4. C4a：在 UART 日志中记录未交付给消费者的 RX 字节速率 `RxDp`。
5. C4b：记录 RTC epoch 和时间源类型。
6. C4c：把超过 64 字节的直接 `Write_Message()` 文本拆成可重组的 MSG 记录。

### 2.2 明确排除

- `cf29484f7d` 的 GCS MAVLink STATUSTEXT 跨包拼接。
- `aac7b5d2a4` 的 AntennaTracker 专用自动测试。

## 3. 总体方案

采用“4.7.0 最终语义手工回植 + 每个功能包独立提交”。除 C1 的 gitlink 更新外，不原样 cherry-pick，也不整体替换 Logger、RTC、Filesystem 或 HAL 文件。

实施顺序：

```text
基线证据
  -> C1 ChibiOS pin
  -> C2 4K/32K FATFS/Logger I/O
  -> C3 armed/safety 日志解耦
  -> C4a UART RxDp
  -> C4c MSG QBBZ
  -> C4b RTC QQB
  -> 全量回归与目标板台架验收
```

C1 和 C2 是同一发布批次但保持两个提交。C4c 先于 C4b，是为了按上游最终 Logger 枚举演进方向处理共享文件，降低手工合并错误。

## 4. C1：ChibiOS SD 恢复

### 4.1 文件与版本

主仓只更新：

```text

88b84600b59d2f39c9d9137aacdc9f098b374b4a
  -> 4f34e21702137a43829501654c283940f8ffe179
```

该范围共 11 个子模块提交、5 个文件，约 `+107/-70`：

```text

```

`dimah743` 使用 SDMMC1 外设，STM32H743 平台实际编译 ChibiOS `SDMMCv2` LLD。USARTv3 变化是 gitlink 跨越 `c6d0293e32` 后随 pin 一起进入的 IRQ callback 支持，必须纳入目标板编译审查，但不是 C4a 计数的功能依赖。

### 4.2 行为

- 错误返回前完成 DMA/bouncebuffer 收尾。
- 修复驱动停止和外设状态机清理。
- 避免错误路径仍等待一个不会完成的 DMA。
- SD 恢复后允许 Logger 线程继续工作。

### 4.3 验收边界

编译只能证明主仓与新 ChibiOS ABI 匹配。C1 的运行验收必须在电机禁用的台架上制造受控的 SD 通信失败、移除和恢复，验证无 watchdog，并验证卡恢复后日志重新增长。

## 5. C2：H7 可回退 32KB I/O

### 5.1 文件

```text
libraries/AP_Filesystem/AP_Filesystem_FATFS.cpp
libraries/AP_Filesystem/AP_Filesystem_FATFS.h
libraries/AP_Filesystem/AP_Filesystem_config.h
libraries/AP_HAL/board/chibios.h
libraries/AP_HAL_ChibiOS/sdcard.cpp
libraries/AP_Logger/AP_Logger.cpp
libraries/AP_Logger/AP_Logger_File.h
```

预计约 68 行 churn。

### 5.2 配置语义

通用默认值：

```text
AP_FATFS_MIN_IO_SIZE = 4096
AP_FATFS_MAX_IO_SIZE = 4096
```

满足 `STM32H7 && HAL_MEM_CLASS >= HAL_MEM_CLASS_1000` 时：

```text
AP_FATFS_MIN_IO_SIZE = 4096
AP_FATFS_MAX_IO_SIZE = 32768
```

`dimah743` 当前生成值为 `HAL_MEMORY_TOTAL_KB=1055`，所以进入 32KB 分支。

### 5.3 初始化和数据流

```text
sdcard_init()
  -> 尝试在 AXI SRAM 分配 32KB bouncebuffer
     -> 成功：FATFS io_size = 32768
     -> 失败：重新分配 4KB，FATFS io_size = 4096
  -> AP_Logger_File 使用 FATFS 的运行期 io_size 作为 write chunk
  -> FATFS 对 DMA-unsafe 的 read/write 按 io_size 分块
```

任何 bouncebuffer 分配都失败时，SD 初始化明确返回失败，不继续使用空 DMA buffer。

### 5.4 本地裁剪适配

- 本地没有 `AP_Filesystem::bytes_until_fsync()`，不新增该接口；继续保持每次 Logger 实际写入后 fsync 的本地语义。
- 本地没有本批所需的 LittleFS 后端，不新增 `AP_FILESYSTEM_LITTLEFS_ENABLED` 或 2048-byte 分支。
- FATFS 使用动态 io size；非 FATFS 保持 `AP_FATFS_MIN_IO_SIZE`，即 4KB。

### 5.5 内存预算

新默认值：

| 分配 | 旧值 | 新值 |
|---|---:|---:|
| SD bouncebuffer | 4KB | 32KB |
| Logger file ring | 200KB | 172KB |
| 合计 | 204KB | 204KB |

Logger 默认计算为：

```text
200 - (32768 - 4096) / 1024 = 172KB
```

若 EEPROM 或外部参数明确保存 `LOG_FILE_BUFSIZE=200`，新编译默认不会覆盖它，总动态分配会增加约 28KB。目标板部署前必须读取该参数，并同时记录 `@SYS/memory.txt`。若 32KB 分配失败并回退 4KB，Logger 默认仍为 172KB，系统会保留约 28KB 额外余量。

## 6. C3：Logger armed 与 safety 解耦

### 6.1 文件

```text
Rover/AP_Arming.cpp
```

### 6.2 状态模型

保留两个不同概念：

```text
hal.util->soft_armed
  = AP arming state && safety switch允许输出

AP_Logger::vehicle_is_armed
  = AP arming state
```

`update_soft_armed()` 只更新输出安全状态，不再反复覆盖 Logger armed 状态。

arm 成功路径：

```text
AP_Arming::arm()成功
  -> Logger set_vehicle_armed(true)
  -> update_soft_armed()
```

disarm 成功路径：

```text
AP_Arming::disarm()成功
  -> 保留现有 mission reset
  -> rover.mode_patrol.clear_points()
  -> Logger set_vehicle_armed(false)
  -> update_soft_armed()
```

arm/disarm 失败时不修改 Logger 状态。重新启用 safety 只停止输出，不停止日志；真正 disarm 才关闭 armed logging。

## 7. C4a：UART RX 丢字节日志

### 7.1 文件

```text
libraries/AP_HAL/LogStructure.h
libraries/AP_HAL/UARTDriver.cpp
libraries/AP_HAL/UARTDriver.h
libraries/AP_HAL_ChibiOS/UARTDriver.cpp
libraries/AP_HAL_ChibiOS/UARTDriver.h
```

### 7.2 schema

```text
旧：UART QBff  TimeUS,I,Tx,Rx
新：UART QBfff TimeUS,I,Tx,Rx,RxDp
```

公共 HAL 增加 dropped counter getter 和 StatsTracker；ChibiOS 在以下路径累计：

- DMA bounce 数据写入 RX ring 时的未写入字节。
- 定时 RX 搬运时的未写入字节。
- begin 重新配置清缓冲时丢弃的已有字节。
- discard input 时丢弃的已有字节。

`RxDp` 表示驱动未交付给消费者的接收字节速率，包括主动丢弃，不等同于纯硬件 overrun。

## 8. C4c：MSG 分片

### 8.1 文件

```text
libraries/AP_Logger/AP_Logger.cpp
libraries/AP_Logger/AP_Logger.h
libraries/AP_Logger/AP_Logger_Backend.h
libraries/AP_Logger/LogFile.cpp
libraries/AP_Logger/LogStructure.h
libraries/AP_Logger/examples/AP_Logger_AllTypes/AP_Logger_AllTypes.cpp
```

### 8.2 schema 和分片

```text
旧：MSG QZ   TimeUS,Message
新：MSG QBBZ TimeUS,ID,Seq,Message
```

一个 `Write_Message()` 调用取得一个非零 8-bit ID，每 64 字节写一个 MSG，Seq 从 0 递增。空字符串仍写 Seq=0 的记录。ID 回绕时跳过 0。

采用 `1d3164d689` 修正后的 example，保证示例 FMT 也为 `QBBZ`。

### 8.3 保留的 4.7 边界

- `Write_MessageF()` 的 65-byte 临时缓冲保持不变。
- 只要求第一片写入失败时返回失败；后续片失败行为保持上游语义。
- `MSG_id` 非原子递增的已知线程竞争不在本批修复。

### 9.2 schema 和触发点

```text
RTC QQB TimeUS,Epoch,SourceType
```

Logger 启动系统信息阶段写一次 RTC；RTC shift 或 source 发生变化时写 RTC 记录。`SourceType` 使用 `AP_RTC::source_type` 的显式值，其中 `SOURCE_NONE=3`。

### 9.3 条件编译

最终设计包含 `fae7dac45f`：

- `AP_RTC_LOGGING_ENABLED = AP_RTC_ENABLED && HAL_LOGGING_ENABLED`。
- `LOG_RTC_MSG` 公共枚举受该宏保护。
- `LoggerMessageWriter::Stage::LOG_RTC_MSG` 受同一宏保护。
- `LoggerMessageWriter.h` 包含 `AP_RTC_config.h`。

RTC logging disabled 的裁剪构建不得出现未处理 enum、未定义 ID 或链接符号。

## 10. 日志 ID 和兼容性

Rover 私有 ID 保持：

```text
THR=0, NTUN=1, STER=2, GUIP=3, XPNV=4, XCAP=5, XHOF=6
```

公共 Logger ID 从 32 开始：

- C4c 只把原槽位 `LOG_MESSAGE_MSG` 重命名为 `LOG_MSG_MSG`，数值槽不变。
- C4b 在公共区增加 RTC，不会与 4/5/6 冲突。
- `LOG_FORMAT_MSG=128` 继续作为显式锚点。
- FMT 自描述解析器可处理公共数字 ID 变化。

兼容性要求：

- Mission Planner 和 pymavlink 都必须能解析新 `.BIN`。
- 私有离线工具若硬编码 `MSG=QZ`、UART 四字段或公共数字 ID，必须在发布说明中标记不兼容。
- XPNV/XCAP/XHOF 的 FMT、结构大小和 ID 不得变化。

### 12.5 目标板台架

- C1：电机禁用，受控 SD 断开/恢复和通信失败；无 watchdog，恢复后日志重新写入。
- C2：高日志速率持续写入，对比 4KB/32KB 的 DSF dropped blocks、写入吞吐、主循环延迟和可用内存；验证分配失败降级。
- C4a：正常负载 `RxDp=0`；制造 RX ring overflow 后 `RxDp>0`；对照 `@SYS/uarts.txt` 的 `RXDRP`，重点覆盖 UM982 所在端口。

- C4b/C4c：下载真实 BIN，检查 RTC 和 MSG 重组。

## 13. 完成标准

只有同时满足以下条件才可声明 C 项完成：

1. 六个原子功能包全部实现并通过对应测试。
2. 工作区原有 `defaults.parm` 修改未被覆盖或提交。
3. SITL debug Rover、RTC-disabled 裁剪构建和 `dimah743 --enable-dds` Rover 均编译链接成功。
4. 所有目标固件产物存在并记录大小。
5. C3 safety 行为在 SITL 中有运行证据。
6. UART、RTC、MSG 的新 FMT 和数据可被 pymavlink 解析。
7. XPNV/XCAP/XHOF ID 和结构保持不变。
8. C1/C2 完成目标板 SD 台架验证；若台架尚未执行，必须把状态写为“编译/SITL 已完成，硬件运行未验证”，不得宣称完整解决。
9. Mission Planner 或项目实际离线工具对新 schema 的兼容性已验证或明确记录迁移要求。
